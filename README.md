## О проекте

**HH Assistant** - это end-to-end (сквозной) ETL-пайплайн и AI-ассистент, разработанный для автоматизации рутинных процессов поиска работы. Проект решает проблему "холодных" откликов, автоматизируя сбор вакансий, семантический анализ текста, генерацию персонализированных писем и трекинг обратной связи от HR.

Это **pet-проект**, демонстрирующий навыки построения данных (Data Engineering), работы с NLP и интеграции с LLM.

## Ключевой функционал (Features)

- **Data Ingestion (Сбор данных):** Использование мобильного API hh.ru (через `hh-applicant-tool`) для обхода ограничений антибот-систем. Умный парсинг с учетом пагинации, периодов публикации, профессиональных ролей и фильтрации по опыту работы.
- **NLP & Semantic Search:** Использование `Cross-Encoder` (модель `DiTy/cross-encoder-russian-msmarco`) для точной семантической оценки релевантности резюме и вакансии.
- **Сравнение навыков:** Интеллектуальный алгоритм сравнивает ключевые навыки из резюме кандидата и заданные ключевые слова с текстом описания вакансии. Работает в связке с NLP: если нейросеть дала высокий балл, но в тексте нет нужных технологий (SQL, Python), вакансия получает понижающий коэффициент.
- **LLM Generation:** интеграция с **GigaChat REST API** для генерации уникальных, коротких и адаптивных сопроводительных писем.
- **Token Rate-Limit Management:** Умный контроль токенов LLM. Если остаток токенов упал до критического минимума (или GigaChat временно недоступен), система автоматически переключается на резервный шаблон (`data/fixed_letter.txt`), чтобы не останавливать процесс отправки откликов.
- **Data Engineering (PostgreSQL):** Проектирование и поддержка реляционной базы данных. Пайплайн ETL для синхронизации вакансий, откликов и переписки с рекрутерами.
- **Concurrent Processing:** Безопасная многопоточная обработка (`ThreadPoolExecutor`) для асинхронного сбора ответов от HR без риска блокировки аккаунта.
- **Надежность и отказоустойчивость:** Логирование всех процессов в файл (`app.log`) и атомарная запись состояния (`state.json`) для защиты от сбоев питания.
- **Тестирование:** Покрытие ключевой логики (фильтрация, дедупликация, парсинг) юнит-тестами (`pytest`).
- **Интерактивный UX:** Русскоязычный интерфейс в терминале с цветовым выделением, валидацией ввода и защитой от случайных ошибок.

## Как работает пайплайн (Data Flow)

Весь процесс управляется через единое главное меню (`main.py`). Вот полная карта всех этапов:

1.  **Настройка (`config.py`)**

Задаем целевые слова для названия вакансии, слова-исключения, профессиональные роли, ключевые слова для описания (и навыки из резюме), опыт и периоды поиска.

2.  **Сбор данных (`vacancy_search.py`)**

Отправляем запросы к API hh.ru, используя выбранные роли и исключения. Собираем новые вакансии в базу `data/vacancies_detailed.json`.

3.  **Матчинг (`matcher.py`)**

Фильтруем мусор по названиям (слова-исключения). Проверяем наличие ключевых слов и навыков из резюме в описании. Пропускаем отфильтрованные вакансии через нейросеть (Cross-Encoder) для точной оценки соответствия. Применяем штрафы за отсутствие ключевых навыков.

4.  **Отклики (`apply_via_api.py`)**

Для вакансий, прошедших порог, генерируем письмо через GigaChat (или берем шаблон) и отправляем отклик через API.

5.  **Тесты (`main.py`)**

Для вакансий, требующих прохождения теста, скрипт генерирует письмо, копирует его в буфер и открывает страницу вакансии для ручного прохождения.

6.  **Синхронизация (`sync_negotiations.py` + `check_messages.py`)**

Выгружаем историю всех откликов и переписку с рекрутерами в реляционную базу данных PostgreSQL.

7.  **Статистика (`main.py`)**

Просмотр текущего прогресса (сколько откликов отправлено, сколько в очереди на тест) и общей истории за все время.

8.  **Сброс прогресса (`main.py`)**

Очистка локального кэша (`state.json`), чтобы можно было заново прогнать матчинг по всем вакансиям.

0.  **Выход**

Завершение работы программы.

## Установка и запуск (Классический способ)

1. **Клонировать репозиторий:**

```bush
git clone https://github.com/ElenaPhoenix/hh-assistant.git
cd hh-assistant
```

2. **Создать виртуальное окружение и установить зависимости:**

```bush
python -m venv venv
source venv/Scripts/activate  # Windows
pip install -r requirements.txt
```

3. **Настроить переменные окружения:**

Скопируй .env.example в .env и заполни своими данными:

```bush
cp .env.example .env
```

**Внутри .env должно быть:**

```bush
* --- hh.ru ---
HH_LOGIN=твой_номер_телефона_без_плюса
HH_PASSWORD=твой_пароль_от_hh

* --- GigaChat (Base64 от Client_ID:Client_Secret) ---
GIGACHAT_AUTH_KEY=твой_длинный_base64_ключ_из_личного_кабинета_sber

* --- PostgreSQL ---
DB_HOST=localhost
DB_PORT=твой_порт
DB_NAME=hh_vacancies
DB_USER=postgres
DB_PASSWORD=твой_пароль_от_базы
```

4. **Инициализировать базу данных (опционально):**

```bush
python db.py  # создаст таблицы
python save_to_db.py  # загрузит существующие JSON в БД
```

5. **Запустить главное меню:**

```bush
python main.py
```

## Запуск через Docker (Для быстрого старта)

## Тестирование

В проекте реализовано комплексное тестирование, покрывающее как отдельные утилиты, так и интеграционные сценарии. Тесты написаны с использованием фреймворка `pytest` и используют **динамическую генерацию данных**, что гарантирует надежность логики при любых входных параметрах (разные запросы, разные резюме, None-значения, спецсимволы).

Для запуска тестов:
```bash
pip install pytest
pytest -v
```

### Что покрывают тесты:
1. **test_filters.py**

Проверяет логику фильтрации названий вакансий. Покрывает: работу слов-исключений (с учетом регистра), логику ИЛИ для целевых фраз (через |), обработку пустых значений и None.

2. **test_utils.py**

Тестирует вспомогательные функции. Проверяет нормализацию текста (приведение к нижнему регистру, замена спецсимволов), очистку от лишних пробелов и переносов, а также URL-кодирование кириллицы и спецсимволов.

3. **test_dedupe.py**

Проверяет алгоритм дедупликации вакансий. Убеждается, что дубли (с учетом регистра и лишних пробелов) схлопываются в один элемент, а вакансии с разными работодателями или разными оценками — остаются.

4. **test_matcher_dynamic.py**

Тестирует ядро логики matcher.py. Проверяет функцию _matches_any_query (что вакансия проходит хотя бы по одному из запросов) и _get_aggregated_skills (что навыки из резюме и ключевые слова из всех запросов корректно объединяются).

5. **test_integration.py**

Интеграционные тесты с изоляцией файловой системы (создание временных config.json, state.json и вакансий). Мокает нейросеть (CrossEncoder) для скорости. Доказывает, что:
* При наличии нескольких запросов в config.json матчер обрабатывает вакансии по всем запросам, а не только по первому.

* Состояния (state.json) разных резюме не смешиваются.

Результат: 14 passed (все тесты зеленые). Это подтверждает, что логика программы устойчива к изменениям конфигурации и ошибкам ввода.

## Технические решения (Why I Built It This Way)

**Почему мобильное API hh, а не Playwright?**

Прямой парсинг через браузер блокируется Group-IB (антибот hh). Мобильное API (hh-applicant-tool) позволяет обходить эти ограничения, работает стабильнее и не требует запуска тяжелых браузеров.

**Как реализован умный фильтр?**

Вместо грубого текстового поиска мы используем справочник professional_roles hh API и сложные поисковые запросы. Локальный фильтр filters.py выступает вторым эшелоном для отсева слов-исключений и проверки ключевых фраз.

**Почему Cross-Encoder, а не обычные эмбеддинги?**

Cross-Encoder обрабатывает пару "резюме-вакансия" одновременно, что дает более точную семантическую оценку релевантности, чем косинусное сходство между отдельными векторами.

**Зачем нужна предфильтрация перед ML?**

Быстрая локальная проверка (слова-исключения, целевые фразы, профессиональные роли) отсеивает 90% нерелевантного мусора до того, как запускать тяжелую нейросеть. Это экономит время и ресурсы CPU.

**Как решена проблема с токенами GigaChat?**

В shared_api.py перехватывается заголовок x-ratelimit-remaining. При достижении порога в 1000 токенов скрипт автоматически переключается на фиксированное письмо из data/fixed_letter.txt.

**Зачем нужна атомарная запись?**

Если скрипт прервется в момент сохранения `state.json`, файл может превратиться в пустой (битый). Атомарная запись через временный файл гарантирует, что при сбое питания старые данные останутся целы.

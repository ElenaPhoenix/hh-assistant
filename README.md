## О проекте

**HH Assistant** - это End-to-End ETL-пайплайн и AI-ассистент для автоматизации поиска работы. Проект охватывает полный цикл: от сбора вакансий через мобильное API hh.ru до генерации уникальных сопроводительных писем через GigaChat и ведения аналитики в PostgreSQL.

Проект создан как демонстрация навыков промышленной разработки (Data Engineering, Python Backend) и решает реальную боль соискателя: избавляет от ручного перебора тысяч вакансий и "слепых" откликов.

## Ключевой функционал (Что демонстрирует код)

**Data Engineering & ETL**

Сбор данных (Extract), очистка и скоринг (Transform), загрузка в реляционную БД (Load). Использование `UPSERT` (`ON CONFLICT DO UPDATE`) и дельта-синхронизации.

**Проектирование БД**

Нормализованная ER-модель (PostgreSQL) с внешними ключами (Foreign Keys). Изоляция транзакций через контекстный менеджер.

**Работа с API**

Интеграция с мобильным API hh.ru (через обертку `hh-applicant-tool`) и REST API GigaChat. Обход антибот-систем (Group-IB), обработка лимитов (Rate Limits), капчи и сетевых сбоев.

**Умный фильтр**

Фильтрация вакансий по 3 независимым критериям с единым алгоритмом нечеткого поиска (`filters.py`).

1. Слова-исключения имеют наивысший приоритет. Если слово или фраза найдены в названии или описании, вакансия отсеивается.
2. Целевые фразы ищутся в названии вакансии.
3. Ключевые слова ищутся в описании вакансии.

Логика поиска для всех 3 критериев идентична: фраза разбивается на слова. Если слово >= 5 символов, допускается 1-2 ошибки (расстояние Левенштейна). Если слово короче или содержит спецсимволы (`C#`, `C++`), требуется точное совпадение. Слова во фразе должны идти подряд в заданном порядке.

**Архитектура ПО**

Принципы DRY и SRP. Безопасная многопоточность (`ThreadPoolExecutor`), атомарная запись файлов (`os.replace`), изоляция субпроцессов (`stdin=DEVNULL`), логирование (`logging`).

**Тестирование**

43 unit- и интеграционных тестов (`pytest`) с полной изоляцией файловой системы и мокированием внешних API.

## Полный функционал (Руководство пользователя)

Вся работа управляется через интерактивное меню `main.py`. Каждый пункт меню решает конкретную задачу.

1. **Настройка поиска (`config.py`)**

Интерактивная настройка конфигурации (`data/config.json`). Создание и редактирование резюме (по URL) и поисковых запросов. Для каждого запроса настраиваются: целевые слова (через `|`), слова-исключения, профессиональные роли hh.ru, ключевые навыки, форматы работы, опыт, периоды публикации, зарплата. Каждый запрос получает уникальный UUID (`q_...`). Здесь же задается общий порог соответствия (`threshold`).

2. **Сбор новых вакансий с hh.ru (`vacancy_search.py`)**

Запросы к API hh.ru с пагинацией. Сбор данных в `data/vacancies_detailed.json`. Поиск разбивается на 2 области (удаленка - весь мир, офис/гибрид - город из резюме) и на периоды (1, 3, 7, 30 дней, все время) для обхода лимита в 2000 вакансий. Сохраняет город (`area_id`) и форматы работы (`work_formats`) для каждой вакансии. При сетевых сбоях (`timeout`) останавливается после 3 ошибок подряд, при серверных ошибках (502) - пропускает вакансию и продолжает работу. Догружает полные описания вакансий, если их нет.

3. **Обработка резюме и матчинг (`resume_parser.py`, `matcher.py`)**

Строгая проверка геолокации: для офисных и гибридных вакансий `area_id` должен совпадать с городом из резюме. Для удаленки город игнорируется. Затем предфильтрация (слова-исключения, целевые фразы, ключевые слова с расстоянием Левенштейна). Скоринг по правилам (title_hits * 40 + kw_hits * 5). Дедупликация. Удаление устаревших записей (без описания) из кэша прогресса. Полный пересчет запускается автоматически при изменении конфига или сбросе прогресса.

4. **Отправка откликов (`apply_via_api.py`)**

Проверка статуса вакансии (архив, тест, уже откликались, лимит). Генерация уникального письма через GigaChat (с `fallback` на шаблон при малом остатке токенов или сбое). Отправка отклика с рандомными паузами (4-7 сек), которые можно прервать нажатием "0". Обработка всех статусов hh.ru, защита от серии ошибок (3 подряд), логирование отправленных писем в `data/letters/`.

5. **Прохождение тестов (`main.py`)**

Выгрузка вакансий из списка `needs_test`. Пользователь может выбрать вакансию для прохождения теста или ввести номера через запятую (например, `1, 3, 5`), чтобы пропустить их (они помечаются как "отказ" и удаляются из списка). При выборе вакансии: генерация письма через GigaChat, копирование в буфер обмена, открытие страницы в браузере для ручного прохождения. После подтверждения отклик считается отправленным.

6. **Синхронизация с hh (`sync_negotiations.py`)**

Скачивание всей истории откликов с hh.ru (с возможностью остановки по "0"). Обновление локального `state.json` (добавление в `applied_vacancy_ids`). Синхронизация с PostgreSQL через `UPSERT`: для новых откликов создается запись с пустым `hh_updated_at` (чтобы пункт 10 гарантированно подхватил переписку), для существующих - обновляется только статус, а `hh_updated_at` сохраняется (чтобы не ломать дельта-синхронизацию).

7. **Статистика (`main.py`)**

Вывод воронки по текущему запросу: всего найдено (с учетом дедупликации), отправлено, ожидают теста, отклонено, осталось обработать. Дополнительно выводится общая история по резюме: всего откликов, всего ожидают теста, всего отказов.

8. **Сброс прогресса (`vacancy_cleanup.py`)**

Очистка локального кэша (`state.json`) и удаление хэша запроса из `matches.json`. Это заставляет матчер сделать полный пересчет с нуля, чтобы применить новые правила фильтрации (город/формат, изменения в словах-исключениях, ключевых словах) к старым вакансиям.

9. **Смена активного запроса (`main.py`)**

Переключение между разными запросами разных резюме. Программа сохраняет `current_resume_index` и `current_query_id` в `state.json`, чтобы все последующие действия (сбор, матчинг, отклики) выполнялись в контексте выбранного запроса.

10. **Проверка ответов работодателей (`check_messages.py`, `show_replies.py`)**

Выгрузка новых сообщений из чатов hh. Используется дельта-синхронизация: сравнивается `updated_at` из hh API с `hh_updated_at` в БД. Если даты совпадают, чат пропускается. Если даты различаются (или в БД пустая строка для нового отклика), сообщения скачиваются в 5 потоков, после чего `hh_updated_at` обновляется на актуальное значение. Затем `show_replies.py` выводит последние 10 переписок с ответами работодателей (от старых к новым) с датой, компанией, названием вакансии и текстом сообщения.

0. **Выход**

Завершение работы программы с логированием события в `data/app.log`.

## Инженерные решения (Архитектура и Edge Cases)

**Почему мобильное API hh, а не Playwright?**

Прямой парсинг через браузер блокируется антибот-системами (Group-IB). Мобильное API (`hh-applicant-tool`) работает в 10 раз быстрее, не требует запуска браузеров и обходит блокировки. При этом система изолирована от зависаний субпроцесса (используется `stdin=DEVNULL`).

**Как работает фильтр по городу?**

В `matcher.py` реализована функция `_check_vacancy_area`. Для форматов "офис" и "гибрид" она строго сверяет `area_id` вакансии с `city_id` из резюме. Если город не совпадает, вакансия отсеивается. Для формата "удаленно" проверка города игнорируется. Если у вакансии нет данных о городе или формате, она принимается (для совместимости), но при следующем запуске сбора данных метаданные обновятся.

**Как работает умный фильтр? (Расстояние Левенштейна)**

Вместо поиска подстроки используется расстояние Левенштейна (`rapidfuzz.distance`). Функция `_phrase_in_text` применяется единообразно для слов-исключений, целевых фраз и ключевых слов. Она разбивает фразу на слова и сравнивает их с текстом: для слов >= 5 символов допускается 1-2 ошибки (опечатки, падежи), для коротких слов и спецсимволов (`C#`, `C++`) - только точное совпадение. Слова-исключения имеют наивысший приоритет: если они найдены, вакансия отсеивается, даже если содержит целевые фразы.

**Как ускорена проверка сообщений от HR?**

Используется дельта-синхронизация. сравнивается поле `updated_at` из API hh с локальной БД. Если даты совпадают, запрос к API не делается. Это сокращает время работы скрипта с 15 минут до 3 секунд при отсутствии изменений.

**Зачем нужен `save_to_db.py`?**

Это утилита для ETL-миграции. Если база данных упадет или нужно пересоздать схему, скрипт зальет все вакансии, резюме и историю откликов из JSON-файлов (`data/`) в PostgreSQL без потери данных.

**Отказоустойчивость и лимиты:**

- **Сеть:** При 3 ошибках сети подряд (при сборе или догрузке) скрипт корректно останавливается, сохраняя прогресс, чтобы не тратить время впустую.
- **GigaChat:** Перехватывается заголовок `x-ratelimit-remaining`. При остатке < 1000 токенов система переключается на шаблон.
- **Атомарная запись:** Все JSON-файлы пишутся через временный файл и `os.replace`. Это гарантирует, что при сбое питания `state.json` не превратится в пустой файл.

**Оптимизация БД:**

Для работы с PostgreSQL используется кастомный контекстный менеджер `db_cursor`. Он автоматически делает `commit`, `rollback` при ошибках и закрывает соединение, избавляя код от дублирования `try/except/finally`.

## Архитектура базы данных (ER-модель)

- **`resumes`**: `id` (PK), `title`, `updated_at`.
- **`vacancies`**: `id` (PK), `name`, `employer`, `salary_from/to`, `full_description`, `area_id`, `work_formats`.
- **`negotiations`**: `id` (PK), `vacancy_id` (FK), `resume_id` (FK), `status`, `hh_updated_at`.
- **`messages`**: `id` (PK), `negotiation_id` (FK), `author_id`, `text`, `created_at`.

## Тестирование и обеспечение качества

В проекте **43 теста** (`pytest`), покрывающих бизнес-логику, утилиты и БД, которые проходят за ~10 секунд.
Главная особенность: полная изоляция файловой системы. В `tests/conftest.py` реализована фикстура `temp_env`, которая перенаправляет все пути (`config.json`, `state.json`, логи) во временную папку. Благодаря этому тесты физически не могут повредить реальные данные пользователя. Также `conftest.py` содержит генераторы случайных данных (`random_string`, `random_id`) для динамических проверок, что гарантирует надежность логики при любых входных параметрах (разные запросы, разные резюме, None-значения, спецсимволы).

Все зависимости для запуска тестов уже включены в `requirements.txt`. Поэтому отдельно ничего устанавливать не нужно.

Для запуска тестов:

```bash
pytest -v
```

### Что покрывают тесты (43 шт.)

**test_apply_via_api.py  (7 тестов)**

Обработка всех статусов API при отправке откликов: архив, требуется тест, неизвестная ошибка, дневной лимит, требуется авторизация, успешная отправка и "уже откликались". Мокирует `send_negotiation` и `generate_letter`, чтобы тесты не тратили реальные токены GigaChat и не делали запросы к hh.ru.

**test_config.py (2 теста)**

Проверка интерактивной смены порога соответствия (`threshold`), а также корректная отмена этого действия без изменения конфига.

**test_db.py (2 теста)**

Проверка контекстного менеджера `db_cursor`. Тесты гарантируют, что при успешном выполнении вызывается `COMMIT`, при возникновении исключения - `ROLLBACK`, а соединение всегда закрывается.

**test_dedupe.py (3 теста)**

Проверка алгоритма дедупликации. Убеждается, что дубли (с учетом регистра и лишних пробелов) схлопываются в один элемент, оставляя лучший результат, а вакансии с разными работодателями или разными оценками - остаются.

**test_filters.py (8 тестов)**

Ядро умного фильтра (`filters.py`). Проверяет расстояние Левенштейна (1-2 ошибки для слов >= 5 символов, точное совпадение для коротких слов и спецсимволов вроде `C#`), приоритет слов-исключений (если есть исключение, вакансия отсеивается, даже если содержит целевые слова) и поиск многословных фраз.

**test_integration.py (3 теста)**

Интеграционные тесты с изоляцией файловой системы (создание временных `config.json`, `state.json` и вакансий). Доказывают, что при наличии нескольких запросов в `config.json` матчер обрабатывает вакансии по всем запросам независимо, а состояния (`state.json`) разных резюме не смешиваются.

**test_matcher_dynamic.py (5 тестов)**

Проверяет логику матчера: поиск по целевому названию, поиск по ключевым словам в описании, агрегацию навыков и функцию `_cleanup_stale_processed` (очистка устаревших записей без описания).

**test_state_helper.py (1 тест)**

Проверяет сохранение прогресса (`applied`, `denied`, `needs_test`) и корректную работу `mark_denied` (при отказе вакансия убирается из списка тестов).

**test_utils.py (5 тестов)**

Тестирует вспомогательные функции. Проверяет нормализацию текста (приведение к нижнему регистру, замена спецсимволов), очистку от лишних пробелов и переносов, а также URL-кодирование кириллицы и спецсимволов, атомарную работу с кэшем вакансий и безопасную запись JSON.

**test_vacancy_search.py (2 теста)**

Проверяет логику экстренной остановки догрузки описаний при 3 сетевых ошибках подряд (защита от зависания), а также успешное сохранение описания, если API вернул данные.

## Установка и запуск (Классический способ)

1. **Клонировать репозиторий и установить зависимости**

**Windows (PowerShell):**

```bush
git clone https://github.com/ElenaPhoenix/hh-assistant.git
cd hh-assistant

# Создать виртуальное окружение
python -m venv venv

# Активировать его
.\venv\Scripts\Activate.ps1

# Установить зависимости
pip install -r requirements.txt
```

Если PowerShell выдал ошибку

```bush
невозможно загрузить файл Activate.ps1, так как выполнение сценариев отключено в этой системе
```

выполните один раз `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` и повторите `.\venv\Scripts\Activate.ps1`.

**Linux / macOS:**

```bush
git clone https://github.com/ElenaPhoenix/hh-assistant.git
cd hh-assistant
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

После активации в начале строки терминала появится (venv):

```bush
(venv) PS C:\Users\User\Desktop\hh_etl_project>
```

2. **Настроить переменные окружения**

Скопируйте .env.example в .env и заполните своими данными (логин hh, ключ GigaChat, доступы к PostgreSQL).

```bush
cp .env.example .env  # Windows: copy .env.example .env
```

3. **Запустить PostgreSQL**

Если установлен как служба Windows: нажмите `Win + R`, введите `services.msc`, найдите `postgresql-x64-XX`, нажмите правой кнопкой -> «Запустить». Служба должна работать в фоне (pgAdmin или DBeaver держать открытыми не нужно).

Если используется Docker: выполните docker-compose up -d db. Контейнер запустится в фоне.

4. **Инициализировать базу данных (опционально, один раз)**

```bush
python db.py  # создаст таблицы
python save_to_db.py  # загрузит существующие JSON в БД
```

5. **Запустить главное меню**

```bush
python main.py
```

## Запуск через Docker (Для быстрого старта)

Если установлен Docker, то можно запустить весь проект (включая PostgreSQL) одной командой:

```bash
docker-compose up -d
docker-compose exec app python main.py
```
